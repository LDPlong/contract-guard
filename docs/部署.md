# 部署说明（演示服务器）

目标：一台 2 核 2G 的云主机，`git clone` + 两条命令就能对外提供访问。

## 部署形态

前端构建产物由后端进程直接托管，**一个进程、一个端口**：

```
浏览器 ──> :8000
            ├── /api/v1/*     FastAPI 接口
            ├── /assets/*     前端静态资源（frontend/dist/assets）
            └── 其余路径       回落到 index.html（SPA 路由）
```

这样做的原因很实际：解析任务、SSE 连接状态、BM25 内存索引都在进程内，本来就必须单进程（`--workers 1`）；再把前端也交给它，演示环境就不需要 nginx 反代和跨域配置。
`frontend/dist` 不存在时（开发态），根路径会返回一段 JSON 说明，接口照常工作。

## 一、裸机部署（已实测）

以 Ubuntu 22.04 为例，Python 3.12、Node 20。

```bash
# 1. 依赖
sudo apt update && sudo apt install -y python3.12 python3.12-venv nginx git
# Node 20：建议用 nvm 安装，避免系统源自带版本过旧

# 2. 取代码
sudo mkdir -p /srv && cd /srv
sudo git clone https://github.com/LDPlong/contract-guard.git
sudo chown -R $USER:$USER contract-guard

# 3. 后端依赖
cd /srv/contract-guard/backend
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp ../.env.example ../.env      # 填入 LLM_API_KEY 等

# 4. 前端构建（产物由后端托管）
cd ../frontend
npm ci && npm run build

# 5. 建法规索引（首次必须，之后改语料才需要重建）
cd ../backend
.venv/bin/python -m scripts.build_index

# 6. 启动
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

打开 `http://<服务器IP>:8000` 即可。安全组 / 防火墙需放行 8000。

### 用 systemd 托管

`/etc/systemd/system/contractguard.service`：

```ini
[Unit]
Description=ContractGuard
After=network.target

[Service]
WorkingDirectory=/srv/contract-guard/backend
Environment=APP_ENV=prod
EnvironmentFile=/srv/contract-guard/.env
ExecStart=/srv/contract-guard/backend/.venv/bin/uvicorn app.main:app \
    --host 0.0.0.0 --port 8000 --workers 1
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now contractguard
sudo journalctl -u contractguard -f
```

### 可选：80 端口 + 域名

有域名时用 nginx 反代，SSE 相关响应头必须关掉缓冲：

```nginx
server {
    listen 80;
    server_name your-domain.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;        # SSE 逐条推送的前提
        proxy_read_timeout 300s;    # 单份合同审查可能跑到 40s
    }
}
```

## 二、Docker（镜像未在本机验证）

仓库根目录有 `Dockerfile`（多阶段：Node 构建前端 → Python 运行）。本机没有 Docker 环境，**这个镜像没有实际跑过**，服务器上第一次请优先走上面的裸机步骤；确认镜像可用后再替换。

```bash
docker build -t contractguard .
docker run -d --name contractguard -p 8000:8000 \
  -e LLM_API_KEY=sk-xxx -e LLM_BASE_URL=https://api.deepseek.com \
  -v /srv/cg-data:/srv/backend/data \
  contractguard
```

容器启动脚本会检查 `INDEX_DIR/bm25.pkl`，缺失时自动执行 `scripts.build_index`，因此挂载空数据卷也能起来（首次多花约 20 秒）。

## 三、演示前检查

```bash
curl -s http://127.0.0.1:8000/api/v1/health
# 期望：{"status":"ok","db":true,"vector":true,"index_built":true,"llm":true,"demo_mode":false,...}
```

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `index_built:false` | 未建索引 | `python -m scripts.build_index` |
| `llm:false` | key 未配置 | 检查 `.env` 的 `LLM_API_KEY` / `LLM_BASE_URL` |
| 打开页面是 JSON | `frontend/dist` 不存在 | `cd frontend && npm run build` |
| 审查卡住无输出 | 反向代理开了缓冲 | nginx 加 `proxy_buffering off` |
| 上传 413 / 失败 | 超过 20MB 或 80 页 | 换小文件，或调 `MAX_FILE_MB` / `MAX_PAGES` |
| 服务重启后文档一直"解析中" | 残留 parsing 记录 | 启动时会自动标记失败，刷新页面重试即可 |

## 四、数据与隐私

- 上传文件存 `backend/data/uploads/`，文件名一律为 UUID；数据库 `backend/data/app.db`。
- 日志只记录文本长度与哈希，不落合同正文。
- 演示环境建议定期清理 `data/uploads` 与 `app.db`，避免把真实合同留在服务器上。
- 对外访问时保留页脚与报告中的"不构成法律意见"声明，这是产品边界，也是合规要求。

## 五、资源占用（实测）

| 项目 | 数值 |
| --- | --- |
| 内存 | 空载约 130 MB（含 BM25 索引 1841 chunk 常驻） |
| 磁盘 | 索引文件 1.8 MB，语料 616 KB，前后端源码约 1 MB（不含 `.venv` 与 `node_modules`） |
| 单份审查 | 15 页合同 10 项判定约 10 秒，其中模型响应占 8 秒以上 |
