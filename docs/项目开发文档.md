## 1. 项目概述

| 项 | 内容 |
|---|---|
| 项目名 | ContractGuard · 合同风险审查官 |
| 一句话 | 上传一份合同，30 秒告诉你哪里会吃亏、依据是哪条法、应该怎么改 |
| 产品定位 | 面向个人的合同**风险提示工具**，非法律意见、不代拟正式文书 |
| 目标用户 | 应届生、实习生、租房青年、初入职场者 |
| 覆盖合同类型 | 房屋租赁合同、实习/劳动合同、培训贷/预付卡协议（**仅这三类**） |
| 技术定位 | AI Native Web 应用：Agent 工作流 + 条款级 RAG + 引用溯源 |
| 交付形态 | Web 应用（前后端分离）+ 可公网访问的演示环境 |

### 1.1 非目标（明确不做，避免范围蔓延）

- 不做通用合同审查（不支持的合同类型直接提示"暂不支持"）
- 不做法律咨询、不预测胜诉率、**不输出可直接签署的完整条文**
- 不做多轮法律问答机器人
- 不做企业级批量审查、电子签章、OCR 手写体识别
- 不做用户体系（MVP 阶段无需注册登录，用匿名 session）
- **不做图片合同的强制支持**（OCR 为 P1，默认关闭，见 F1b）

### 1.2 合规定位边界（重要，影响 F6 与第 11 节措辞）

本产品的输出是**风险提示 + 示例性修改方向**，不是条款起草服务。两者的界限必须体现在文案和字段命名上：

| 允许 | 禁止 |
|---|---|
| 指出"该条款缺少退还时限，实践中易被拖延" | 输出"甲方应于……7 日内……"这类可直接粘贴进合同的完整条文 |
| 给出"建议补充退还时限，常见做法是 7-15 日内"这类**方向性描述** | 以"正式条款文本"命名任何字段 |
| 提示"可以这样沟通：……"（谈判话术） | 声称修改后的条款"合法有效""一定能胜诉" |

实现要求：`findings.suggestion` 字段语义为 **「修改方向说明」**，前端展示标题固定为「建议方向」，且每条建议下方强制渲染免责行（见 14 节）。

## 2. 核心功能（P0 必须 / P1 应当 / P2 可选）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| F1 | 合同上传与解析（文字版 PDF） | P0 | PDF 文本层抽取，返回解析状态 |
| F1b | 图片合同 OCR 解析 | P1 | 拍照/扫描件，`OCR_ENABLED=true` 时启用，默认关闭 |
| F2 | 条款级切分与定位 | P0 | 按"第X条/第X款"切分，保留页码与 PDF 点坐标 bbox |

| F4 | 风险条款高亮 | P0 | 双栏对照，左栏 pdf.js 渲染原页 + 叠层高亮，点击定位 |

| F6 | 修改方向 + 谈判话术 | P0 | 输出**方向性说明**（非完整条文）与沟通话术，措辞见 1.2 |
| F7 | 安全评分与报告导出 | P1 | 总分 + 分级统计，导出 PDF |
| F8 | 隐私脱敏 | P1 | 身份证/手机号/银行卡自动打码，可选不落库 |
| F9 | 低置信度兜底 | P1 | 置信度 < 阈值时折叠并提示人工复核 |

## 3. 技术栈（固定，不得替换）

### 3.1 前端

| 项 | 选型 | 版本要求 |
|---|---|---|
| 框架 | Vue 3（Composition API + `<script setup>`） | ^3.4 |
| 语言 | TypeScript | ^5.3 |
| 构建 | Vite | ^5 |
| 路由 | Vue Router | ^4 |
| 状态 | Pinia | ^2 |
| 样式 | Tailwind CSS | ^3.4 |
| 请求 | axios（普通接口） | — |
| **SSE 客户端** | **`fetch` + `ReadableStream` 手动解析 SSE 帧** | 浏览器原生 |
| PDF 渲染 | pdf.js（`pdfjs-dist`） | ^4.x |
| 图标 | lucide-vue-next | — |

> ❌ **禁止使用原生 `EventSource`**。审查接口为 `POST`（需携带 options 与鉴权头），而 `EventSource` 只支持 GET 且不能自定义请求头，无法满足契约。前端统一用 `fetch` + `getReader()` 解码 `text/event-stream`，解析逻辑封装在 `api/review.ts` 的 `streamReview()`，**不得在组件内重复实现**。

### 3.2 后端

| 项 | 选型 | 版本要求 |
|---|---|---|
| 语言 | Python | 3.11+ |
| 框架 | FastAPI | ^0.115 |
| 服务器 | uvicorn（**单 worker 启动**，见 3.4） | ^0.30 |
| ORM | SQLAlchemy 2.0（async） | ^2.0 |
| 校验 | Pydantic v2 | ^2.7 |
| PDF 解析 | PyMuPDF（fitz） | ^1.24 |
| 表格/文本抽取 | pdfplumber（辅助） | ^0.11 |
| OCR | PaddleOCR | ^2.7（**可选，默认关闭**，见下） |
| 向量检索 | **numpy（内存向量 + `.npz` 持久化）** | — |
| 词法检索 | rank_bm25 + jieba | ^0.2 |
| 重排 | 内置 `RERANK_ENABLED=false`，默认走 RRF 截断；需要时接 API 型 rerank | — |
| 报告导出 | **reportlab（定死，不用 WeasyPrint）** | ^4.0 |
| 测试 | pytest + httpx | — |

**选型说明（均为 v1.1 收敛结果，不接受回退）**：

- **向量检索不用 Chroma**：法条语料规模在 1000-5000 chunk 量级，numpy 一批矩阵乘即可，单次检索 < 5ms；同时避开 Chroma 同步客户端在 async 路由中阻塞事件循环、必须包 `run_in_executor` 的隐藏坑。语料超过 2 万 chunk 再评估引入向量库，且需要单独评审。
- **重排默认关**：`FlagEmbedding` 本地加载 bge-reranker 需数百 MB 模型、首请求冷启动 3-8 秒，与"总耗时 ≤ 40s"冲突。先用 RRF 融合结果直接取 top 5，评测不达标再开 API 型 rerank。
- **报告不用 WeasyPrint**：Windows 下依赖 GTK（pango/cairo）运行库，安装成功率低且难在 README 里写清。reportlab 纯 Python，零系统依赖。
- **OCR 默认关**：PaddleOCR + PaddlePaddle 在 Windows/Python 3.11 上安装失败率高、包体近 1GB，且演示样本以文字版 PDF 为主。`OCR_ENABLED=false` 时图片上传返回 `1002` 并提示"请上传文字版 PDF"。若要开，优先接云 OCR（一次 HTTP 调用），**不要求本地部署 PaddleOCR**。

### 3.3 模型服务（通过 OpenAI 兼容协议接入，可切换）

| 用途 | 默认模型 | 环境变量 |
|---|---|---|
| 对话/审查 | deepseek-chat（可切换 qwen-plus） | `LLM_MODEL` |
| 向量化 | bge-m3（1024 维）或 text-embedding-3-small（1536 维） | `EMBEDDING_MODEL` |
| 重排 | 关闭时不使用 | `RERANK_MODEL` |

> **重要**：模型调用必须封装在 `services/llm/client.py`，通过环境变量切换供应商，禁止在业务代码里硬编码任何模型名或 BaseURL。
>
> **向量维度不写死**：`EMBEDDING_DIM` 不放入 `.env`。`build_index.py` 首次建索引时探测实际维度并写入 `data/index/meta.json`，检索时校验不一致则直接报错并提示重建索引（避免"换模型后维度不匹配"的静默错误）。

### 3.4 存储与运行约束

| 项 | 选型 | 说明 |
|---|---|---|
| 关系库 | SQLite（开发/演示） | `DB_URL=sqlite+aiosqlite:///./data/app.db`，**必须开启 WAL** |
| 向量索引 | `data/index/vectors.npz` + `bm25.pkl` | 随 `build_index.py` 生成 |
| 文件 | 本地 `data/uploads/` | 演示环境足够 |

**运行约束（写进 README，违反会导致状态错乱）**：

1. **uvicorn 必须 `--workers 1`**。异步解析任务、SSE 连接状态、BM25 内存索引都驻留在单进程内，多 worker 会导致任务丢失与索引不一致。
2. SQLite 连接建立后立即执行 `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;`，否则 SSE 长连接期间写入 findings 会 `database is locked`。
3. 服务启动时执行一次状态修复：把 `documents.status IN ('parsing')` 且 `created_at` 超过 5 分钟的记录置为 `failed`，`error_msg='服务重启，解析中断'`。

## 6. 数据模型

### 6.1 DDL（SQLite 方言，PostgreSQL 可平滑迁移）

```sql
CREATE TABLE documents (
    id            TEXT PRIMARY KEY,          -- uuid4
    session_id    TEXT NOT NULL,             -- 匿名会话标识，前端首次访问生成并持久化于 localStorage
    filename      TEXT NOT NULL,             -- 原始文件名（仅展示用）
    stored_name   TEXT NOT NULL,             -- 磁盘实际文件名（uuid，防路径穿越与重名）
    file_path     TEXT NOT NULL,
    mime_type     TEXT NOT NULL,
    size_bytes    INTEGER NOT NULL,
    sha256        TEXT NOT NULL,             -- 同一 session 内去重
    contract_type TEXT,                      -- lease | labor | prepaid | unknown
    type_source   TEXT,                      -- rule | llm | user | unknown
    page_count    INTEGER DEFAULT 0,
    status        TEXT NOT NULL,             -- uploaded|parsing|parsed|failed
    error_msg     TEXT,
    created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_documents_session ON documents(session_id, created_at);

CREATE TABLE clauses (
    id          TEXT PRIMARY KEY,
    document_id TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    seq         INTEGER NOT NULL,            -- 全文顺序，从 1 开始
    clause_no   TEXT,                        -- "第三条" / "3.2" / 无编号时为 NULL
    page_no     INTEGER NOT NULL,
    bbox_json   TEXT,                        -- [x0,y0,x1,y1]，单位 PDF point，左上原点，绝对坐标
    text        TEXT NOT NULL,
    char_start  INTEGER,                     -- 在全文中的起始偏移
    char_end    INTEGER
);
CREATE INDEX idx_clauses_doc ON clauses(document_id, seq);

CREATE TABLE reviews (
    id                TEXT PRIMARY KEY,
    document_id       TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    status            TEXT NOT NULL,         -- pending|running|done|partial|failed
    safety_score      INTEGER,               -- 0-100，越高越安全（算法见 10.2）
    summary           TEXT,
    model             TEXT,
    prompt_version    TEXT NOT NULL,
    checklist_version TEXT NOT NULL,         -- 规则版本，审计与复现必需
    demo_mode         INTEGER NOT NULL DEFAULT 0,
    latency_ms        INTEGER,
    started_at        TIMESTAMP,
    finished_at       TIMESTAMP
);
CREATE INDEX idx_reviews_doc ON reviews(document_id);

CREATE TABLE findings (
    id              TEXT PRIMARY KEY,
    review_id       TEXT NOT NULL REFERENCES reviews(id) ON DELETE CASCADE,
    clause_id       TEXT REFERENCES clauses(id) ON DELETE CASCADE,
    risk_level      TEXT NOT NULL,           -- high|medium|low
    category        TEXT NOT NULL,           -- 押金|违约金|解除权|转租|维修|试用期|竞业...
    title           TEXT NOT NULL,           -- 一句话结论
    reason          TEXT NOT NULL,           -- 为什么有风险
    legal_basis_json TEXT NOT NULL,          -- [{source,article,quote,chunk_id}]
    suggestion      TEXT NOT NULL,           -- 修改方向说明（非完整条文，措辞见 1.2）
    negotiation_tip TEXT,                    -- 谈判话术
    confidence      REAL NOT NULL DEFAULT 0, -- 0-1，0 表示该项调用失败需人工复核
    priority        TEXT NOT NULL DEFAULT 'yieldable', -- must|negotiable|yieldable（v1.2）
    impact          TEXT NOT NULL DEFAULT '',  -- 白话影响，一句话（v1.2）
    needs_review    INTEGER NOT NULL DEFAULT 0, -- 1=依据不足 / 自动判定未完成（v1.2）
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_findings_review ON findings(review_id, risk_level);

CREATE TABLE knowledge_docs (
    id             TEXT PRIMARY KEY,
    source         TEXT NOT NULL,            -- 民法典|劳动合同法|司法解释|地方规定
    title          TEXT NOT NULL,
    article_no     TEXT,                     -- "第五百八十五条"
    version        TEXT,                     -- 版本/修正年份
    effective_date DATE,                     -- 生效日期，用于时效提示
    content        TEXT NOT NULL,
    checksum       TEXT NOT NULL UNIQUE      -- 唯一约束保证并发建索引也幂等
);
```

**模型层面的三条硬约定**：

1. **`safety_score` 而非 `risk_score`**：字段语义是"越高越安全"，与扣分制评分算法一致。命名反过来会让前端环形图必然画反。前端展示文案为「安全分 42/100」，不使用"风险评分"。
2. **`findings.clause_id` 用 `ON DELETE CASCADE`**：删除条款时保留悬空结论会直接断掉"点结论定位原文"这条核心交互。宁可删结论，不留悬空引用。
3. **没有独立 session 表**：`session_id` 是前端生成、随请求头 `X-Session-Id` 传入的字符串，只作为过滤维度，不做身份认证。缺省时后端生成并回传。

### 6.2 向量索引文件结构（替代 v1.0 的 Chroma 集合）

```
data/index/
├── meta.json      # {model, dim, built_at, chunk_count, corpus_checksum}
├── vectors.npz    # {ids: str[], matrix: float32[N,dim]（已 L2 归一化）}
└── bm25.pkl       # {ids: str[], tokenized: list[list[str]]}
```

- 切分粒度：**法条级**（一条一 chunk），超过 800 字再按段落切，overlap 100
- `ids` 为 `knowledge_docs.id`；两套索引的 `ids` 顺序必须一致，检索后按 RRF 融合
- 启动时校验 `meta.json.dim` 与当前 `EMBEDDING_MODEL` 探测维度一致，不一致直接拒绝服务并提示重跑 `build_index.py`

## 7. RAG 流水线

### 7.1 离线索引（`scripts/build_index.py`）

```
corpus/*.md → 按"第X条"解析为条目 → 清洗 → 计算 checksum 去重
      → 写入 knowledge_docs 表（checksum UNIQUE，冲突即跳过）
      → 向量化（batch=16，L2 归一化）→ 写 vectors.npz
      → jieba 分词 → 构建 BM25 索引 → 写 bm25.pkl
      → 写 meta.json（记录 dim / chunk_count / corpus_checksum / built_at）
```

要求：
- 幂等：重复执行不产生重复条目（checksum 判重 + DB 唯一约束双保险）
- 输出统计：条目数、耗时、失败条目清单
- 每条必须带 `effective_date`，缺失时告警
- 结束时打印 `chunk_count` 与 `dim`，与 `meta.json` 一致

### 7.2 在线检索（`services/rag/retriever.py`）

```
query（条款原文 + 审查项名称）
   ├─ BM25 召回 top 20
   ├─ 向量召回 top 20（归一化后点积 = 余弦）
   ├─ RRF 融合（k=60）→ 合并去重 top 20
   ├─ rerank 精排（RERANK_ENABLED=false 时直接截断）→ top 5
   └─ 命中为空 → 返回 []，由上层输出"未覆盖"结论
```

- 必须实现 **RRF 融合**，而不是简单加权分数（量纲不同）
- 返回结构统一为 `RetrievedChunk{chunk_id, content, score, article_no, source, effective_date}`
- 检索耗时上限 800ms，超时降级为仅向量检索
- 索引未构建（`meta.json` 缺失）时，`/health` 的 `vector` 字段返回 `false`，审查接口返回 `3002`

## 8. 接口契约

统一前缀 `/api/v1`，统一响应包装：

```json
{ "code": 0, "message": "ok", "data": { } }
```

错误码：

| code | 含义 | HTTP |
|---|---|---|
| 0 | 成功 | 200 |
| 1001 | 参数错误 | 400 |
| 1002 | 文件类型不支持 | 415 |
| 1003 | 文件过大 / 页数超限 | 413 |
| 1004 | 会话无效或缺失 | 400 |
| 2001 | 解析失败 | 422 |
| 2002 | 合同类型不支持 | 422 |
| 2003 | 异步任务仍在进行 | 202 |
| 3001 | 模型调用失败 | 502 |
| 3002 | 检索无结果 / 索引缺失 | 503 |
| 4290 | 触发限流 | 429 |

> **SSE 接口例外**：`8.4` 的流式响应体是裸的 `text/event-stream`，**不使用 `{code,message,data}` 包装**。错误通过 `event: error` 帧传递，`data` 内仍是 `{code, message}`。前端需分别处理两种格式。

所有请求可携带 `X-Session-Id` 头；缺失时由后端生成并通过响应头 `X-Session-Id` 返回。

### 8.1 上传合同

`POST /api/v1/documents` · `multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| file | File | 是 | pdf/jpg/jpeg/png，≤ 20MB，≤ 80 页 |
| contract_type | string | 否 | 用户手动指定，缺省自动识别 |

响应：

```json
{
  "code": 0,
  "data": {
    "document_id": "d1f3...",
    "status": "parsed",
    "contract_type": "lease",
    "type_source": "rule",
    "page_count": 6,
    "clause_count": 24
  }
}
```

**同步/异步策略（v1.1 明确定义）**：

- 解析在请求内**同步执行**，硬超时 `PARSE_TIMEOUT_SEC=10`。
- 未超时 → 直接返回 `status=parsed`。
- 超时 → 返回 `code=2003, data.status=parsing`，文档记录保持 `parsing`，前端按 1s 间隔轮询 `GET /documents/{id}`。
- 超时后**不续跑**（MVP 不引入 Celery/RQ，避免任务队列这一整层基础设施）。前端轮询累计超过 60 秒（`MAX_PARSE_WAIT`）仍为 `parsing` 时，提示"解析超时，请重试或上传更小的文件"。
- 服务重启时由启动自检把残留 `parsing` 置为 `failed`（见 3.4）。
- 该设计的前提是 **uvicorn 单 worker**；引入多 worker 前必须先把解析改成外部队列。

```json

```

> 传输方式：**POST + `fetch` 流式读取**。禁止 `EventSource`（只支持 GET、不能带 body 和自定义头）。

事件流（每条 `data:` 一个 JSON）：

```
event: step
data: {"step":"plan","status":"running","message":"识别为房屋租赁合同，加载 10 项审查清单"}

event: step
data: {"step":"gate","status":"running","message":"条款预筛：24 条条款 → 9 条进入判定"}

event: error
```

前端必须处理：
- `done` 前断开 → 展示"连接中断，已获取 N 条结果" + 重试按钮

- `stance`：立场声明，说明结论默认站在哪一方
- `open_question`：「清单之外的一个问题」，提示清单未覆盖但影响签约决策的盲区
- `framework_flags`：框架审阅命中的结构性观察列表

`finding` 帧与 `done.findings[]` 每项新增 `priority`（`must|negotiable|yieldable`）、
`impact`（白话影响）、`needs_review`（是否需人工复核）。三者均不参与 `safety_score` 计算。

## 9. 条款级切分规则（核心算法）

`clause_splitter.py` 必须实现以下规则，按顺序尝试：

1. **编号识别正则**（按优先级）
   - 中文条：`第[一二三四五六七八九十百零〇]+条`
   - 中文款：`第[一二三四五六七八九十]+款`
   - 阿拉伯多级：`^\d+(\.\d+){0,3}[、.．\s]`
   - 括号编号：`^[（(][一二三四五六七八九十\d]+[)）]`
2. **段落兜底**：无编号时按空行/换行切分，且单块 ≤ 600 字
3. **合并规则**：连续短段落（< 30 字且不以句号结尾）合并到上一块，避免标题被单独切开
4. **坐标回填**：用 PyMuPDF 的 `page.search_for()` 或 `get_text("dict")` 的 span bbox，把每块文本映射回页码与矩形
5. **偏移记录**：记录 `char_start/char_end` 相对全文，便于前端做文本级高亮（pdf.js 渲染失败时的降级方案）

### 9.1 验收口径（v1.1 补充，避免"准确率"无法计算）

对 3 份真实脱敏合同人工标注基准切分（`tests/fixtures/*.gold.json`），按**条款条数**计算：

- `切分准确率 = 与基准边界完全一致的条款数 / 基准条款总数`（允许 ±1 条的边界抖动，不计入错误）
- `bbox 定位准确率 = bbox 与人工标注框 IoU ≥ 0.5 的条款数 / 有基准框的条款总数`
- 目标：切分 ≥ 90%，bbox ≥ 85%
- 脚本：`scripts/evaluate.py --splitter`，输出逐条 diff 便于定位问题

### 9.2 bbox 坐标系约定（v1.1 新增，前端必须遵守）

| 项 | 约定 |
|---|---|
| 单位 | PDF point（1/72 inch） |
| 原点 | 页面**左上角**，y 轴**向下**（PyMuPDF 默认） |
| 数值 | **绝对坐标**，不是归一化比例；`[x0, y0, x1, y1]` |
| 前端换算 | pdf.js viewport 已含 rotation 与 scale，直接用 `viewport.convertToViewportRectangle(bbox)` 得到设备像素框，**不要自己乘 scale** |
| 跨页条款 | 一条条款跨页时，`bbox` 只存**起始页**的框，`page_no` 记起始页；完整高亮由 `char_start/char_end` 做文本级兜底 |

### 9.3 合同类型识别（v1.1 新增，`type_detector.py`）

三级策略，命中即停：

1. **用户指定**：请求带 `contract_type` 且属于三类之一 → `type_source=user`
2. **规则打分**：按关键词命中数打分（如"押金/租金/出租人/承租人"→ lease；"试用期/用人单位/劳动者"→ labor；"培训/课程/贷款/退费"→ prepaid），最高分 ≥ 3 且领先第二名 ≥ 2 → `type_source=rule`
3. **LLM 兜底**：取首 800 字 + 条款标题列表，单次分类调用，`type_source=llm`
4. 全部失败或结果不在三类内 → `contract_type=unknown`，审查接口返回 `2002`，前端提示"暂不支持该合同类型"

阈值与关键词表放在 `core/constants.py`，不得散落在业务代码里。

## 10. Agent 工作流

```
plan（识别合同类型 → 加载 checklist 与 version）
  ↓
gate（条款预筛：条款 × 审查项候选映射，剔除不相关组合）  ← v1.1 新增，见 10.1
  ↓
for each (checklist_item, candidate_clauses):
    retrieve（工具调用：search_law(query, top_k=5)）
    judge（LLM 判定：命中/未命中 + 风险等级 + 依据 + 建议方向）
  ↓
aggregate（去重、按风险等级排序、计算安全分、生成摘要）
  ↓
persist（写 findings、更新 review）
```

### 10.1 条款预筛与 Prompt 上下文构造（v1.1 新增，成本与耗时命门）

v1.0 缺这一层，导致"每项审查都把全合同喂给模型"——token 爆炸、40 秒目标不可能达成。规则如下：

**Step 1 · 候选召回（`agent/gating.py`）**

- 以 checklist item 的 `keywords + name` 作为 query，对**本文档的条款集合**做 BM25 打分（不用向量，条款数量小、关键词信号强）
- 每个 item 取 top 5 条款，且分数需 ≥ `GATE_MIN_SCORE`（默认 3.0）
- 候选为空 → 该 item 标记 `not_applicable`，**不调 LLM**，不计入分母
- 特例：`必备条款缺失` 类 item（L09）不看条款正文，只看文档的 `clause_no` 与标题列表，命中判定交给 `check_missing` 工具

**Step 2 · 上下文构造（`agent/prompts.py`）**

单次 judge 的 prompt 只包含：

| 片段 | 上限 |
|---|---|
| 审查项定义（name / risk_rule / weight） | 150 字 |
| 候选条款原文（≤5 条，每条截断 400 字） | 2000 字 |
| 检索到的法条（top 5，每条截断 300 字） | 1500 字 |
| 输出格式约束 | 200 字 |

- 单次 prompt 硬上限 **3000 tokens**，超出按"条款优先级 + 检索分数"截断并在日志告警
- **禁止把整份合同全文放进 prompt**，禁止把 checklist 全部条目一次性塞入
- 十条审查项并行时，实际进入 LLM 的组合数应显著少于 `10 × 条款数`，典型为 `10-20 次调用`

**Step 3 · 结果归并**

- 同一 clause 被多个 item 判为风险 → 按 `risk_level` 取最高，`category` 保留第一个，`title` 拼接上限 30 字
- 同一 item 命中多个条款 → 合并为一条 finding，`clause_id` 取最高分条款

### 10.2 Function Calling 工具定义（`agent/tools.py`）

| 工具名 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `search_law` | `query: str, top_k: int = 5` | `chunks[]` | 检索法规库 |
| `get_clause` | `clause_id: str` | `{text, clause_no}` | 按 id 取条款原文（避免全文入 prompt） |
| `check_missing` | `contract_type, present_categories[]` | `missing[]` | 检测缺失必备条款 |
| `calc_safety_score` | `findings[], missing[]` | `score: int` | 计算安全分 |

> ~~`compare_template`~~ 已从 P0 工具集移除：v1.0 定义了该工具但语料库中没有"标准模板库"，属于无数据支撑的接口。F12（对比）为 P2，实现时再补 `data/templates/`。

评分算法（固定，不要交给模型）：

```
基础分 100
每处 high 扣 12，每处 medium 扣 5，每处 low 扣 2
缺少必备条款每项扣 8
最终 clamp 到 [0, 100]，字段名 safety_score
```

### 10.3 并发与超时

- 审查项 3 并发（全局 `LLM_MAX_CONCURRENCY` 闸门，跨请求共享，注意 API 限流）
- 单条超时 25 秒
- 单条失败不中断整体，标记 `confidence=0` 并在汇总中提示
- 总耗时目标 ≤ 40 秒（30 页合同）；M4 联调时必须实测并记录，未达标先调 `gate` 阈值而不是加并发

### 10.4 依据充分性闸门与框架审阅（v1.2 新增）

**依据充分性闸门**（强化第 19 节禁止项 #5）：

- `resolve_refs()` 精确通道与 `search()` 补充检索合并后，命中数为 0 时**不调用模型**，
  直接产出 `risk_level=none` / `needs_review=1` 的「依据不足，未下结论」卡片。
- 门槛 `MIN_LEGAL_BASIS_CHUNKS=1`：清单项是细粒度单条规定，`legal_refs` 是人工校过的精确法条，
  一条即可；律师级法律研究要求的 ≥5 条不适用于本产品。
- `missing_check` 模式例外：它的结论来自「合同里缺哪个词」的文本规则，不依赖法条推理。
- 闸门不改变 `safety_score` 算法；`review.status` 仍按 `needs_review` 置 `partial`。

**框架审阅**（`agent/framework.py`，纯规则、零模型调用，聚合阶段执行）：

- 四问：义务单向性 / 退出权不对等 / 违约对称性 / 虚假前提。
- 命中一律 `risk_level=low`（提示级），`item_id` 为 `F01`~`F04`；
  证据条款经 `clause_seq` 回填，前端仍能点结论定位原文。
- 只统计「单主体句」：中文条款常把甲乙双方写在同一句，共现句无法用规则判定归属，直接跳过；
  退出权判断必须用主体紧邻动作的短窗口正则，不能用跨主体的宽窗口。
- 阈值在 9 份评测样本上标定：6 份问题样本命中 4 份（预付卡 / 培训贷不适配框架四问），
  3 份官方示范文本**零误报**；不改变清单项的召回口径。

**结论呈现层**（不参与评分）：

- `priority`：high → 必守；medium 命中法定权利 / 已付款项 / 退出权关键词 → 必守，否则可谈；low / none → 可让步。
- `impact`：按类别映射的一句白话影响。
- `stance` / `open_question`：立场声明与「清单之外的一个问题」，写入 `done` 事件，报告首页展示。
- `PROMPT_VERSION` 升 `judge-1.2`，保证历史结论可区分、可复现。

## 11. LLM 输出契约（JSON Schema）

系统提示词必须要求模型**只输出 JSON**，不允许 Markdown 代码块包裹。

```json
{
  "type": "object",
  "required": ["hit", "risk_level", "category", "title", "reason", "legal_basis", "suggestion", "confidence"],
  "properties": {
    "hit":        { "type": "boolean", "description": "该审查项在条款中是否构成风险" },
    "risk_level": { "type": "string", "enum": ["high", "medium", "low", "none"] },
    "category":   { "type": "string" },
    "title":      { "type": "string", "maxLength": 30 },
    "reason":     { "type": "string", "maxLength": 200 },
    "legal_basis": {
      "type": "array",
      "minItems": 0,
      "items": {
        "type": "object",
        "required": ["source", "article", "quote", "chunk_id"],
        "properties": {
          "source":   { "type": "string" },
          "article":  { "type": "string" },
          "quote":    { "type": "string" },
          "chunk_id": { "type": "string" }
        }
      }
    },
    "suggestion":      { "type": "string", "maxLength": 300 },
    "negotiation_tip": { "type": "string", "maxLength": 150 },
    "confidence":      { "type": "number", "minimum": 0, "maximum": 1 }
  }
}
```

**硬性约束（写进系统提示词）**：

1. `legal_basis` 中的 `chunk_id` **必须来自检索结果**，不得编造；无检索结果时 `legal_basis` 返回空数组，`confidence` ≤ 0.5
2. `hit=false` 时其余字段可为空，但仍需返回完整结构
3. 不得输出法条编号以外的法条内容（防止幻觉改写）
4. 不得给出"胜诉率""一定有效"等确定性表述
5. 输出语言为简体中文
6. **`suggestion` 只写"建议方向 + 常见做法"，不得输出可直接粘贴进合同的完整条文**；不得出现"甲方应……乙方应……"这类正式条款句式，改为"建议补充……，常见做法是……"

解析兜底：JSON 解析失败 → 重试 1 次（追加"只输出 JSON"）→ 仍失败则记录原始文本（**不落库正文，只记录前 200 字与哈希**），返回 `hit=false, confidence=0`，并在摘要中提示该项需人工复核。

## 13. 前端页面与交互

### 13.1 页面结构

| 路由 | 页面 | 内容 |
|---|---|---|
| `/` | HomeView | 价值主张 + 上传区 + 三类合同说明 + 隐私声明 |
| `/review/:docId` | ReviewView | 左原文右结论的双栏审查台 |

### 13.2 审查台布局

```
┌──────────────────────────────────────────────────────────┐
│ 顶栏：文件名 · 合同类型 · 安全分环 · 导出报告             │
├───────────────────────────┬──────────────────────────────┤
│ 左栏（60%）                │ 右栏（40%）                   │
│ pdf.js 原页渲染            │ Agent 步骤条（折叠）           │
│ + bbox 叠层高亮            │ 结论卡片列表（按等级排序）      │
│ 高/中/低 三色底纹           │ 每卡片：标题/理由/法条/建议方向/话术│
│ 点击条款 → 右栏联动滚动     │ 置信度 < 0.6 折叠为"待复核"     │
└───────────────────────────┴──────────────────────────────┘
```

**左栏实现要点（v1.1 明确）**：

1. pdf.js 加载 `GET /documents/{id}/file`，逐页 canvas 渲染，容器内滚动
2. 高亮层为绝对定位的 `div` 覆盖在对应 page 的 canvas 上，位置由 `viewport.convertToViewportRectangle(bbox)` 计算
3. 缩放（zoom / fit-width）变化时**必须重算所有高亮框位置**，否则框会漂移
4. pdf.js 加载失败（文件被删、损坏）时降级为纯文本渲染，用 `char_start/char_end` 做字符级高亮
5. 每个高亮框 `data-clause-id`，点击后 `$emit('select', clauseId)`，由父组件驱动右栏滚动

### 13.3 状态机

```
idle → uploading → parsing → ready → reviewing → done
                        ↓            ↓
                      failed       partial（部分失败仍展示）
```

- `reviewing` 时右栏逐条插入卡片（流式），顶部进度条显示 `done/total`
- SSE 断开：展示"连接中断，已获取 N 条结果"+ 重试按钮
- 任一环节失败不得白屏，必须有错误卡片与"重新上传"入口
- `DEMO_MODE=true` 时顶栏显示「演示模式（模拟数据）」角标

### 13.4 视觉规范

- 主色 `#2F6FED`，风险色：高 `#E5484D`、中 `#F5A524`、低 `#30A46C`
- 字体：系统字体栈 + `PingFang SC` / `Microsoft YaHei`
- 圆角 8px，卡片阴影 `0 1px 3px rgba(0,0,0,.06)`
- 全部中文界面，移动端宽度 < 768px 时改为上下堆叠（左栏改为按条款逐条文本展示，不渲染 PDF）
- 安全分环形图：**数值越高填充越多、颜色越绿**；低于 60 用风险色，60-80 用中色，80 以上用低风险色

## 16. 代码规范

### 16.1 通用

- 命名：Python `snake_case`，TS `camelCase`，组件 `PascalCase`，常量 `UPPER_SNAKE`
- 注释：公开函数必须有 docstring/JSDoc；复杂算法（切分、RRF、预筛）必须写清思路
- 禁止：`print` 调试（用 logger）、魔法数字（提到 `core/constants.py`）、超 80 行的函数
- Git：`feat:` / `fix:` / `docs:` / `refactor:` / `chore:` 前缀；**保留完整提交历史，禁止 squash 成一个提交**（比赛要求体现开发过程）

### 16.2 后端

- 路由层只做参数校验与编排，业务逻辑放 `services/`
- 所有 DB 操作走 async session，禁止在路由里裸写 SQL
- Pydantic schema 与 SQLAlchemy model 分离，禁止混用
- 外部调用（LLM/OCR/Embedding）统一走 `services/llm/client.py`，带 timeout、重试与全局并发闸门
- **禁止在 async 路由里调用任何同步阻塞库**（numpy 除外，纯内存计算）

### 16.3 前端

- 全部 `<script setup lang="ts">`，禁止 Options API
- 类型定义集中在 `src/types/index.ts`，与后端 schema 一一对应
- 组件 props/emits 必须显式声明类型
- 请求统一走 `api/http.ts`（普通接口）与 `api/review.ts`（SSE），禁止组件内直接 `fetch`

### 17.2 评测（`scripts/evaluate.py`，写进技术文档）

**评测集规模（v1.1 收敛）**：共 **9 份**人工标注合同，三类各 3 份（1 份干净、2 份含风险）。v1.0 要求 20 份，标注工作量本身就要 2-3 天，且署名标注者不明会导致指标无说服力——宁可少而实。

**标注规范（写入 `docs/annotation.md`，标注前必须先定）**：

- 标注单位：`(clause_id, checklist_item_id, risk_level)`
- 什么算 high：可能造成**直接经济损失**或**丧失核心权利**（如押金不退、单方解除、天价违约金）
- 什么算 medium：权利义务明显失衡但可通过协商修正
- 什么算 low：表述不规范、缺少一般性约定，实际影响有限
- 两人独立标注，分歧由第三人裁决；计算 **Kappa 一致性 ≥ 0.7** 后指标才可信

输出指标：

| 指标 | 定义 | 目标 |
|---|---|---|
| 高风险召回率 | 标注 high 的条款中被检出的比例 | ≥ 85% |
| 高风险准确率 | 检出 high 中确为 high 的比例 | ≥ 75% |
| 依据可溯率 | 有 legal_basis 且 chunk_id 在库中真实存在的结论占比 | ≥ 95% |
| 平均耗时 | 30 页合同端到端 | ≤ 40s |

**这些数字要写进技术文档和演示视频**，是区别于"套壳 demo"的最硬证据。同时必须附**失败案例**（至少 2 条漏检或误报），主动暴露问题比全绿更可信。

## 19. 明确禁止事项（AI 编码助手最容易跑偏的地方）

1. ❌ 不得把 API Key、真实合同文件、`.env` 提交到仓库
2. ❌ 不得擅自更换技术栈（如 Vue 换 React、FastAPI 换 Flask）
3. ❌ 不得引入文档未列出的重型依赖（LangChain、LlamaIndex、Chroma、FlagEmbedding 等，如确需使用必须先说明理由并获确认）
4. ❌ 不得让模型直接输出 Markdown 混排文本（必须是纯 JSON）
5. ❌ 不得在无检索结果时编造法条
6. ❌ 不得跳过 bbox 坐标回填（否则前端无法高亮，等于核心功能失效）
7. ❌ 不得把评分算法交给模型（必须代码实现，保证可复现）
8. ❌ 不得删除或重写已有的 Git 提交历史
9. ❌ 不得在日志中打印完整合同正文
10. ❌ 不得把"暂不支持"的合同类型强行审查（必须明确拒绝）
11. ❌ 不得用 `EventSource` 实现审查接口（契约是 POST）
12. ❌ 不得把整份合同全文塞进单次 LLM 调用（必须走 10.1 预筛）
13. ❌ 不得在 `suggestion` 中输出可直接签署的完整条文（违反 1.2 合规定位）
14. ❌ 不得把 `safety_score` 命名为 `risk_score` 或在 UI 表述为"风险越大分越高"
15. ❌ 不得以多 worker 方式启动 uvicorn（破坏解析任务与内存索引的一致性）

## 20. 附录：术语与设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 为什么条款级切分而非固定长度 | 按"第X条"切 | 法条与合同条款的最小语义单位是"条"；固定切分会把一条拆两半，导致漏判和引用错位 |
| 为什么用清单驱动而非自由审查 | 30 条固定 checklist | 输出稳定、可评测、可复现；自由审查容易被模型漏项且无法量化 |
| 为什么必须有引用 | legal_basis 强制绑定 chunk_id | 法务场景没有依据的结论等于没有结论；同时直接对应"AI 可解释性"评分项 |
| 为什么评分算法写死 | 代码计算 | 模型打分不可复现，评委会质疑；固定权重可解释、可调参 |
| 为什么只做三类合同 | 范围收敛 | 每类 6-10 项清单可做到高准确率；泛化反而全线平庸 |
| 为什么 DEMO_MODE | 离线兜底 | 评审现场网络不可控，演示必须 100% 可跑 |
| 为什么 SSE 用 fetch 而非 EventSource | 契约是 POST | EventSource 只支持 GET 且不能带自定义头，与请求体契约冲突 |
| 为什么前端要 pdf.js 渲染原页 | bbox 高亮必须有承接方 | 纯文本重排版会让 bbox 失去意义，等于砍掉核心卖点 |
| 为什么必须在 judge 前做预筛 | 控制 token 与耗时 | 全合同 × 全部审查项的笛卡尔积无法在 40s 内跑完，成本也不可接受 |
| 为什么向量检索不用 Chroma | 语料规模小 | 数千 chunk 用 numpy 足够，且避开同步库阻塞事件循环的坑 |
| 为什么 `safety_score` 不叫 `risk_score` | 语义与算法一致 | 扣分制算出来的是"安全度"，命名反了前端必画错 |
| 为什么 OCR 默认关 | 安装与体积成本高 | Windows + PaddleOCR 成功率低，演示样本以文字版为主 |
