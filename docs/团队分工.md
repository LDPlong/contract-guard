## 一、成员与职责

| 代号 | 角色 | 主要交付物 | 对应评分维度 |
|---|---|---|---|
| **A**（队长） | 架构与全栈开发 | 系统架构设计、前端全部页面与交互、Agent 工作流与 RAG 检索、后端 API、部署与运维、代码审查 | AI 技术深度 35%、前端工程质量 10%、用户体验中的交互 3% |
| **B** | 数据与质量 | 法规语料整理与版本核对、三类审查清单种子数据、合同样本收集与脱敏、评测集标注、缺陷跟踪与回归 | AI 技术深度中的 RAG 6% 与 AI 安全可控 4%、实用性 10% |
| **C** | 产品与交付 | 需求调研与用户访谈、信息架构与视觉稿、技术文档撰写与排版、演示视频脚本与剪辑、提交材料打包与合规检查 | 创新性 25%、用户体验中的 UI 4%、社会价值与商业潜力 10% |

**A 承担全部代码实现**，B、C 的交付物是代码之外的比赛必备材料（语料、清单、标注、文档、视频）。这不是"挂名"——第 18 节的交付清单里，技术文档 ≤30 页、演示视频 5-8 分钟、评测集标注都是独立且耗时的工作，谁做谁署名。

### 为什么这样分

评分表里 65% 的分值（AI 技术深度 35% + 前端工程 10% + 交互 3% + 实用性里的方案有效性 5% + UI 4% + 文档相关）落在这三条线上，三个人正好对上，不存在"有人没事干"或"有人被架空"。

## 二、按目录划分 ownership（避免提交冲突）

| 路径 | Owner | 说明 |
|---|---|---|
| `frontend/**` | A | 全部前端代码 |
| `backend/app/services/**`、`backend/app/api/**` | A | 业务逻辑与接口 |
| `backend/app/data/corpus/**` | **B** | 法规原文，按来源分文件 |
| `backend/app/data/checklists/**` | **B** | 三类审查清单 JSON（改内容必须升 `version`） |
| `backend/tests/fixtures/**` | **B** | 脱敏合同样本与标注金标准 |
| `docs/**` | **C**（技术部分由 A 提供素材） | 技术文档、架构图、评测报告 |
| `deliverables/**` | **C** | 视频脚本、PDF 终稿、提交清单 |

**规则**：跨 ownership 的修改走 PR 或先沟通，禁止直接 push 别人目录（B、C 不写业务代码，避免引入未评审的实现）。

## 三、提交规范（评委要看真实开发过程）

### 3.1 提交信息格式

```
<type>(<scope>): <中文描述>

type:  feat | fix | docs | refactor | test | chore | perf | style
scope: parse | split | rag | agent | api | ui | doc | ci | data
```

示例：

- `feat(split): 实现条款级切分与 bbox 回填`
- `fix(api): 修正上传接口超时未返回 2003 的问题`
- `docs(团队): 补充三人分工与协作规范`
- `data(checklist): 补充培训贷 P04 冷静期审查项`

### 3.2 提交粒度

- **一个可验证的改动一次提交**，不要攒一整天再提交
- 单个 commit 变更文件建议 ≤15 个
- 提交前必须能通过本地验证（后端 `pytest`、前端 `npm run build`）
- **禁止 squash 历史**，禁止 `--amend` 已推送的提交

### 3.3 各成员的提交领域

| 成员 | 提交范围 | 建议频率 |
|---|---|---|
| A | `feat/fix/refactor` 涉及 `frontend/`、`backend/app/services`、`backend/app/api` | 每个功能点一次 |
| B | `data(...)`、`test(...)` 涉及 corpus / checklists / fixtures | 每批语料或标注完成时 |
| C | `docs(...)` 涉及 `docs/`、`deliverables/` | 文档每完成一节 |

### 3.4 身份配置（B、C 首次提交前）

B、C 在自己机器的仓库根目录执行，**只对本仓库生效**，不影响全局配置：

```bash
git config user.name "成员B姓名"
git config user.email "成员B邮箱"
```

### 3.5 分支策略

- `main` 为可运行状态，保持随时可演示
- 大功能在 `feat/<模块>` 分支开发，完成后合并回 `main`
- 9 天窗口内不追求严格 PR 流程，但**禁止 force push 覆盖他人提交**
