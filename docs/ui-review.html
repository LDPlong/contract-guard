已脱离模板感，但结论没站在第一排

视觉语言（纸感、墨色、锐角、法条可追溯）已经形成自己的性格，这是大多数参赛作品做不到的。 真正拖后腿的是两件事：信息层级——用户最该先看到的"哪里有问题"被压成 11px 小字； 以及移动端根本没有适配——390px 下按钮被压成竖排单字、PDF 横向溢出。

01

先明确：这几件事不要动

改版最容易死在"什么都想优化"

纸感底色 + 墨色三层 保留

#FBFAF7 暖白替代纯白、#15171C 替代纯黑，长时间读合同眼睛不累，也贴合"法律文书"的心智。这是全站最值钱的一层，换掉就变成又一个 Tailwind 模板。

2px 锐角 + 几乎不用阴影 保留

圆角卡片 + 大阴影是 AI 生成页面的典型指纹。这里刻意走印刷品路线，判断是对的。只有 pill 按钮做了例外，那是功能性选择，可以留。

每条结论必带法条编号 + 原文引用 保留

这是产品真正的差异点——"AI 说的"变成"民法典第七百三十三条说的"。问题只在于它现在被排成 11px 灰字埋在展开区里，价值被浪费了（见 P1-04）。

「契」印章字标 保留

比任何图标库的盾牌/放大镜都有辨识度，而且和藏青色、衬线标题是同一套语言。别换成通用 icon。

02

问题清单

按"是否会毁掉一次演示"排序
P0

必修：现在就会出事

5 项 · 约 2.5 小时
P0-01

390px 下顶栏按钮被压成竖排单字，变成三个圆圈

位置
ReviewView.vue 第 105–124 行，标题行右侧的动作区
现象
「导出报告」「重新审查」四个字逐个换行，按钮被撑成 80px 高的圆球，安全分被挤到左上，整条顶栏失去阅读顺序。这是评审当天一定会被看到的画面。
原因
flex items-center gap-4 既不允许换行，也没给按钮 shrink-0，flex 收缩把中文按字断行。
改法
容器改 flex flex-wrap items-center gap-3；按钮补 shrink-0 whitespace-nowrap。
≤640px 时「导出报告」降级为 40×40 的图标按钮（Printer），只留「重新审查」文字，两个按钮的总宽控制在 200px 内。
P0-02

移动端「原版」PDF 横向溢出，右侧被裁掉

位置
ClauseViewer.vue paintPages() 第 80–81 行
现象
手机上看合同，页面右半截看不见——"合同编号"的填空线、"出租人 / 承租人"签名栏全在可视区外，而且没有横向滚动条，等于看不到也滑不到。
原因
缩放基准 Math.max(available, 460) 的 460px 硬下限：390px 屏上容器只有约 330px，页面仍按 460px 渲染。
改法
下限降到 320，并补 Math.min(available, 容器宽) 双重约束；≤640px 时初始 mode 直接取 'text'，不让用户在没有缩放能力的小屏上看原版排版。
P0-03

手机首屏给的是合同封面，结论要滑两屏才出现

位置
ReviewView.vue 第 186 行的栅格
现象
桌面端是"原文左 / 结论右"，lg: 断点一撤，原文整块排到最前。用户上传合同后第一眼看到的是「广东省住房租赁合同示范文本」封面和一堆空白填空线，看不到任何一条风险。
原因
DOM 顺序即视觉顺序，没有为移动端做优先级重排。
改法
<1024px 时先渲染结论区（分数 + 前三条命中的条款），原文收进「查看原文」全屏抽屉。桌面端保持现状。
P0-04

次要文字对比度 3.11:1，却承载着法条依据和置信度

位置
tailwind.config.js → ink.faint = #8A8F98；全站 10–11px 说明文字
现象
实测：paper 底 3.11:1、白底 3.25:1。WCAG AA 正文要求 4.5:1，而它被用在法条引用、置信度、审查耗时、命中条款标签、页脚免责声明上——恰好都是"需要被读到"的内容。
原因
token 值偏亮，又被大量小字号叠加，两个不利因素相乘。
改法
ink.faint → #6B7078（paper 4.77:1 / white 4.98:1，过线且不发黑）；另设 ink.ghost = #9AA0A8 只给装饰性分隔和禁用态，不承载信息。
P0-05

正文字号整体偏小：中文 12px 读起来费劲

位置
结论卡 reason 12px、法条 11px、.label 10px；原文 12.5px
现象
中文没有西文的小写字母高度，12px 下的汉字笔画糊在一起。评委在投影或笔记本上看，第一批被放弃的就是这些字。
原因
整体字号表是照着"信息密度优先"定的，但这份产品的阅读负担本来就重（法条原文 + 三段分析）。
改法
正文基线 14px，辅助 12px，label 11px（配 tracking .08em）。结论卡：标题 13→15px、reason 12→13.5px/1.85、法条 11→12.5px；原文条款 12.5→15px/1.95。行宽控制在 34–38 个汉字。
P1

该修：决定作品是"能用"还是"专业"

9 项 · 约 5 小时
P1-01

结论没有第一层级：安全分和工具按钮抢同一行

位置
ReviewView.vue 第 105–124 行
现象
「安全分 88 / 条款较规范」与「导出报告 / 重新审查」并排，视觉权重几乎相同；而"6 处低风险"这个真正的结论，被排成下一行 11px 的 高 0 中 0 低 6。
原因
把"结果展示"和"页面操作"塞进了同一个 flex 容器。
改法
拆成两层：标题行只放文档信息 + 图标化工具；结论条独立成块，给分数、三档计数和一句话摘要，占右栏顶部 88px。见下方对照图 A。
P1-02

「审查过程」跑完后仍占着 190px 固定高度

位置
AgentTrace.vue，以及它在右栏 flex 列中的位置
现象
流式结束后，四个已完成步骤仍然完整展示，把结论列表往下推。审查过程是过程信息，结论才是结果信息，过程不该长期占用结果的位置。
改法
streaming=false 后折叠成一行：✓ 审查完成 · 9.6s · 10/10，点击展开回看步骤；流式期间保持展开，正好当进度反馈。
P1-03

命中条款 chips 顺序是随机的（第三条 → 第十条 → 第九条…）

位置
ReviewView.vue riskyClauses，按 store.findings 顺序渲染
现象
用户想找"第十条"时，得从左到右扫一遍——因为顺序既不是条款序，也不是风险序，而是模型返回顺序。这是看起来没问题、用起来很烦的那类细节。
改法
按 clause_no 的数字部分升序；如果希望引导谈判顺序，就按「必守 → 可谈 → 可让步」分组，组内再按条款号。二选一，别混。
P1-04

法条依据被 11px 灰字埋在展开区——这是产品最强的点，却是最弱的视觉

位置
FindingPanel.vue 第 122–138 行
现象
「法律依据 / 民法典 第七百三十三条 + 引文」三行 11px ink-faint，缩进在卡片深处，需要先展开、再往下读。而它恰恰是"可信 AI"的全部证据。
改法
折叠态就在卡片底部露一行：依据 民法典 第七百三十三条（12.5px，藏青色，可点跳法规库）；展开后才显示引文全文。把"可追溯"做成卡片的一等公民，而不是脚注。
P1-05

结论卡默认展开，一次点开三条就变成信息瀑布

位置
FindingPanel.vue expanded 状态
现象
每条展开后有"法律依据 / 可能影响 / 建议方向 / 沟通建议"四段，单卡能到 400px 高。多卡同开时，用户失去"还剩几条"的空间感。
改法
改成手风琴：同时只展开一条，切换时收起上一条；首条默认展开保留，但只展开到"原因"段，依据/影响/建议做成二级展开。
P1-06

免责声明刷了三遍，稀释了每一条结论的分量

位置
footer（App.vue 92 行）、每张结论卡底部（FindingPanel.vue 158 行）、答疑面板底部
现象
同一句话在滚动区里重复出现 6 次以上，读者的注意力被训练成"跳过灰字"，连真需要看的法条也一起被跳过。
改法
删掉结论卡里的那句，保留 footer 一处 + 导出报告页脚一处 + 答疑面板一处。三处都是"边缘位置"，符合免责声明的实际作用。
P1-07

法规库两个搜索框，用户不知道该用哪个

位置
LawLibraryView.vue：页头「检索条文，如：押金 返还」+ 列表头「在本法规内筛选」
现象
两个输入框，都在页面中部，视觉上像同一个功能的两种样子。用户要么两边都试，要么两边都不敢用。
改法
合并成一个：搜索框固定在页头，占位文案随侧栏选中项变化——选《民法典》时显示「在民法典内检索，共 1260 条」，点全库显示「检索五部法律」。侧栏加"全部法规"项作为作用域开关。
P1-08

法规列表每条都重复「民法典」，占掉行首最贵的位置

位置
LawLibraryView.vue 条文行：第一条 民法典
现象
同一部法下面 1260 行都在重复"民法典"，等于把最容易扫读的左侧位置浪费在常量上。
改法
单一法视图下省略法名，只留条号；跨法检索结果里才显示来源。条号用衬线、字号 +1，法名降为后缀小字。
P1-09

右下角「问」按钮压在结论卡上

位置
AssistantDock.vue，fixed right-5 bottom-6
现象
在审查台里，它正好盖住右栏结论卡的右下角（截图中遮住了"建议方向"的末行）。而审查台恰恰是最需要"边看边问"的场景。
改法
审查台内把入口内联到右栏底部：就这份合同提问 →；全局浮动按钮只在首页/法规库/说明页出现。既解决遮挡，也让"提问"和"当前合同"建立上下文关系。

06

建议不要做

改版的另一半是克制
✕不要换字体族。现在这套"衬线标题 + 苹方正文"是对的，换成 Inter 或思源黑体会立刻失去文书感；只调字号和字距。
✕不要加渐变、发光、玻璃拟态。产品卖点是"可信"，任何装饰性特效都在削弱它。
✕不要为了"看起来 AI"加打字机动画。流式输出本身已经是动效，再加一层就是噪音。
✕不要引入组件库。现在是手写 token + 少量 component 类，只有 6 个组件，引入 Element/Ant 只会把风格拉回模板。
✕不要把"安全分"做成仪表盘/圆环。细横条 + 大数字已经足够，圆环会把它变成游戏化评分，与"不构成法律意见"的克制立场冲突。
✕不要给 6 处低风险都配彩色底。风险色只做左侧色条或小标签，整片染色会让页面变成交通灯。
评审依据：frontend/src 全部组件与 tailwind.config.js；实机渲染覆盖 1440×940、390×844 两档宽度，以及答疑面板打开态。 对比度按 WCAG 2.1 相对亮度公式实测，非估算。
本报告只提修改方向，未改动任何源码。
